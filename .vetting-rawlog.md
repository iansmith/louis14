## Citation 3 — ComputeIsFixedContainer + ComputeIsAbsoluteContainer (layout_object.cc ~1520-1580)

**Plan body claims:** ComputeIsFixedContainer returns true when any of:
(a) HasTransformRelatedProperty()
(b) Position != kStatic || HasWillChangeProperty(kPosition) [but asymmetry: kPosition only flows to abspos]
(c) TransformStyle3D() == kPreserve3d
(d) ShouldApplyPaintContainment(style) || ShouldApplyLayoutContainment(style) [consulting kContain will-change]
(e) HasFilterInducingProperty() / HasBackdropFilter()
(f) HasNonInitialOffsetPath()
(g) Root exception: early-return for LayoutView/document element

**Reality at SHA:**
File path correct: `third_party/blink/renderer/core/layout/layout_object.cc`.
Actual locations:
- `ComputeIsFixedContainer` at **line 1852** (plan said ~1520-1580; off by ~280)
- `ComputeIsAbsoluteContainer` at **line 1905**

Signature: `bool LayoutObject::ComputeIsFixedContainer(const ComputedStyle& style) const`
— **`const ComputedStyle&` reference, NOT `const ComputedStyle*` pointer** (plan repeatedly says pointer).

Body conditions (verbatim 1852-1902):
1. `if (IsViewTransitionRoot()) return true;`
2. Document-element-gated: `if (!is_document_element && style.HasNonInitialFilter()) return true;`
3. Document-element-gated: `if (!is_document_element && style.HasNonInitialBackdropFilter()) return true;`
4. **`LayoutView` IS a fixed container** (line 1874): `if (IsA<LayoutView>(this) || IsSVGForeignObject() || IsTextControl()) return true;`
5. Fieldset anonymous: returns true if parent is fieldset and parent is a fixed container.
6. `if (style.HasTransformRelatedProperty() || style.TransformStyle3D() == kPreserve3d) { if (IsBox()) return true; }`
7. `if (IsEligibleForPaintOrLayoutContainment() && (ShouldApplyPaintContainment(style) || ShouldApplyLayoutContainment(style) || style.HasWillChangeProperty(CSSPropertyID::kContain))) return true;`
8. `return false;`

ComputeIsAbsoluteContainer (1905-1915):
```
return is_fixed_container ||
       (style.GetPosition() != EPosition::kStatic ||
        style.HasWillChangeProperty(CSSPropertyID::kPosition)) ||
       (IsAnonymous() && Parent() && Parent()->IsFieldset() &&
        Parent()->CanContainAbsolutePositionObjects());
```

Signature: `ComputeIsAbsoluteContainer(const ComputedStyle& style, bool is_fixed_container)`
— **parameter ORDER reversed** vs plan: plan has `(bool is_fixed_container, const ComputedStyle* style)`,
actual is `(style, is_fixed_container)`.

**Deltas vs plan:**
- ✗ Plan's "root early-return for LayoutView" is **FALSE**. LayoutView IS a fixed container (line 1874).
  The root exception is more subtle: only filter/backdrop-filter are gated by `!is_document_element`
  (lines 1859, 1865). HasTransformRelatedProperty etc still fire for the root.
- ↻ HasNonInitialFilter/HasNonInitialBackdropFilter are the actual function names checked in this
  function — plan names `HasFilterInducingProperty()` / `HasBackdropFilter()` are not what
  ComputeIsFixedContainer calls. (HasFilterInducingProperty exists at computed_style.h:2177 but
  is broader; ComputeIsFixedContainer uses the narrower HasNonInitialFilter.)
- ✗ Plan's `HasNonInitialOffsetPath()` does **NOT EXIST**. The offset-path will-change effect
  flows through `HasWillChangeAnyTransformProperty()` → `HasTransformRelatedProperty()`.
- Plan's enumeration of "containment will-change uses HasWillChangeProperty(kContain)" — confirmed
  at line 1898 (explicit `style.HasWillChangeProperty(CSSPropertyID::kContain)` call).
- The `is_fixed_container` flag DOES participate in `ComputeIsAbsoluteContainer` (line 1908) — confirmed,
  plus the kPosition will-change asymmetry is real (line 1910): kPosition will-change contributes
  only to absolute container, not to fixed (the call in ComputeIsFixedContainer doesn't check kPosition).
- Pointer/reference and parameter-order are stylistic but the plan code-snippets would not compile;
  worth fixing.

Status: **↻ updated** — line off; signatures wrong (ref vs pointer, param order); root exception
description is wrong; HasNonInitialOffsetPath is a fabricated function name.

  at **lines 1256-1262**.

**Important delta:** plan's claim "The general 'would this property create a stacking context'
determination consults the same HasWillChangeProperty accessor" is in the WRONG FILE.
- `style_adjuster.cc` does NOT consult will-change at all (`grep WillChange` returns zero matches).
- The actual will-change → SC determination lives in
  `ComputedStyle::CalculateIsStackingContextWithoutContainment` at
  `computed_style.cc` line **2927**.
- That function calls a static helper
  `HasPropertyThatCreatesStackingContext(WillChange(), AllowsZIndex())` at
  `computed_style.cc` line **1319** — this is where the canonical will-change → SC property set

The set enumerated at lines 1326-1352:

kContain, kViewTransitionName,

Plan's enumerated stacking set is mostly right, BUT:
- Plan lists `mask` (shorthand) — Blink stores only `mask-image` (and `WebkitMaskBoxImageSource` =
  mask-border equivalent). The plan correctly identifies this elsewhere (line 80 "mask shorthand vs
  mask-image longhand mismatch") but then re-lists `mask` in the Phase 1 SC set (line 298). Plan is
  internally inconsistent.
- Plan misses: `offset-position`, `-webkit-box-reflect`.

Status: **↻ updated** — line range was approximately right (1117-1400) but the architectural
attribution is wrong: ForcesStackingContext/AllowsZIndex live in style_adjuster.cc; the will-change
→ SC bitmask check lives in `computed_style.cc` `CalculateIsStackingContextWithoutContainment` +
`HasPropertyThatCreatesStackingContext` helper. **THIS CITATION MUST BE ADDED.**

## Architectural risks (no DESIGN ESCALATION)

The plan's approach DOES survive at this SHA. The canonical model
(`StyleWillChangeData`/`resolved_longhand_ids`) is intact. The CB and SC routing through
`HasWillChangeProperty` plus the helper functions is intact. The "fold the per-call-site keyword
match into one resolved model" plan still maps 1:1 onto Blink's architecture.

The one nuance the plan's Phase 3 description gets *philosophically* wrong is the root exception.
Plan says "LayoutObject::ComputeIsFixedContainer early-returns for the LayoutView". Reality: LayoutView
IS a fixed container in Blink. The "root exception" is narrower — only filter/backdrop-filter are
gated by `!is_document_element`. For louis14's purposes, this MAY OR MAY NOT matter: louis14's
`isRoot` branch (block_layout.go:1772) already routes the root differently (resolves everything
against viewport), so the plan's "gate the new will-change CB branches on `!isRoot`" guidance is
operationally correct for louis14 even though the Blink justification is misstated. The fix is to
correct the Blink description without changing the louis14 plan.

No architecture-level escalation needed.
